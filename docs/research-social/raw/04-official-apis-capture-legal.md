# Official APIs, assisted-capture techniques, and legal landscape for post-level social metrics

Retrieved 2026-09-14 unless noted. All claims are sourced; anything not confirmed by a primary source is marked **[unverified]**. This is research, not legal advice.

Goal: get post-level metrics (dates, likes, comments, views) for a prospective client + 2–3 competitors, per platform, legitimately and for free where possible, from a local Windows/Node app.

## 1. Official APIs that expose OTHER accounts' public data

### Summary table

| Platform | Free official path for a *competitor's* post-level data? | Verdict |
|---|---|---|
| Instagram | Yes, via Graph API `business_discovery`, but only reliably in production if the app gets Advanced Access (App Review + Business Verification) | Best official option, with friction |
| Facebook Pages | Formally yes (Page Public Content Access) but Meta has been tightening/replacing this with researcher-gated Meta Content Library; hard for a commercial agency to get approved in 2026 | Weak/uncertain |
| YouTube | Yes, fully, for any public channel/video, free API key, generous quota | Best official option overall |
| TikTok | No — Research API is academic/nonprofit-only and explicitly excludes commercial use; Display API only covers the authenticated user's own account; Commercial Content API is ads-library only | No viable free official path |
| LinkedIn | No — Community Management API only reads pages/analytics you administer | No official path for competitors |
| X (Twitter) | Technically yes but no free tier since Feb 2026 — pure pay-per-use ($0.005–0.01 per read) | Official, but not free |
| Snapchat | Only for opted-in Public Profiles via partner relationship; not for arbitrary businesses | No practical path |

### 1.1 Instagram Graph API — Business Discovery

**What it returns.** The `business_discovery` field lets an Instagram professional (Business/Creator) account query metadata for *another* Business/Creator account: `id, username, website, name, profile_picture_url, biography, followers_count, follows_count, media_count`, plus a nested `media` edge with `id, caption, media_type, media_url, timestamp, like_count, comments_count` (and `view_count` for video/Reels). Endpoint shape: `GET /<YOUR_IG_USER_ID>?fields=business_discovery.username(<target_username>){followers_count,media_count,media{caption,like_count,comments_count,timestamp,media_type}}`.
Source: [Business Discovery — Meta for Developers](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login/business-discovery/) (retrieved 2026-09-14); corroborated by [Using Instagram Graph API to access any business account followers and media count](https://www.ficode.com/blog/using-instagram-graph-api-access-business-account-followers-media-count) and a Medium walkthrough [Get other Instagram Users' data using Business Discovery](https://medium.com/@ritikkhndelwal/get-other-instagram-users-data-using-the-python-and-instagram-graph-api-business-discovery-807ba4a9ad91).

**Requirements.**
- The *querying* account (Al-Marketer's own account) must be an Instagram **Business or Creator** account connected to a Facebook Page — not a personal account. Personal-account targets are unsupported: querying a personal (non-business) target returns an "unsupported request" error, because the Graph API only indexes professional accounts. Source: [Instagram Graph API Complete Developer Guide 2026](https://elfsight.com/blog/instagram-graph-api-complete-developer-guide-for-2026/) and a Meta developer community thread on the exact error, [Instagram business discovery error](https://developers.facebook.com/community/threads/310930884925810/) (retrieved 2026-09-14). This directly answers the question: **it does not work for personal accounts** — expected, confirmed.
- Permissions needed on the querying account's token: `instagram_basic`, `instagram_manage_insights`, `pages_show_list` (older Facebook-Login-based Instagram API), per [Correct Permissions for Instagram Login via Facebook API](https://medium.com/@python-javascript-php-html-css/correct-permissions-for-instagram-login-via-facebook-api-8eb9dcf65ff1) and Meta's [Permissions Reference](https://developers.facebook.com/docs/permissions/) (retrieved 2026-09-14). Newer Instagram-API-with-Instagram-Login apps use `instagram_business_basic` instead.
- **App Review / Business Verification.** Meta's access model has two levels: **Standard Access** (works only for accounts you own/manage, added as Admin/Developer/Tester in the App Dashboard — no App Review needed, app can stay in Development Mode) and **Advanced Access** (required if the app "serves Instagram professional accounts you don't own or manage" — requires App Review *and* Business Verification). Source: [Meta for Developers — Permissions Reference](https://developers.facebook.com/docs/permissions/), and [Instagram API Advanced Access Approval Guide (2026)](https://singhamandeep.com/instagram-api-advanced-access-approval/) (retrieved 2026-09-14).
  **Applied to Business Discovery: [unverified, but likely]** — Business Discovery targets (competitors) don't authenticate or grant anything, so in principle the querying account's own Standard Access token could work. However, Meta's general Development Mode rule is that an app "will not be able to... access the data of any users who aren't associated with the app" (source: [Facebook developer blog — Live Mode for production use](https://developers.facebook.com/blog/post/2019/09/23/live-mode-for-production-use/), retrieved 2026-09-14), and third-party guides describe Business Discovery itself as subject to the same Standard/Advanced split for "accounts you don't own." **Practical recommendation: assume Advanced Access (App Review + Business Verification) is required to reliably query competitor accounts in production**, and test against a real competitor handle in Development Mode first to confirm whether it errors before investing in App Review — the actual restriction is not stated explicitly enough in primary docs to be 100% certain either way.
- **Business Verification** requires proving the legal business identity in Meta Business Manager (company documents) — free, but takes time and paperwork. Source: [Instagram API Advanced Access Approval Guide (2026)](https://singhamandeep.com/instagram-api-advanced-access-approval/).

**Rate limits.** Business Discovery and Hashtag Search are excluded from the standard Business Use Case (BUC) formula (`4800 × impressions/24h`) and instead subject to Meta's Platform Rate Limits, with a commonly cited figure of **2 calls/second per Instagram professional account**. Source: [Instagram Graph API Complete Developer Guide 2026](https://elfsight.com/blog/instagram-graph-api-complete-developer-guide-for-2026/) (retrieved 2026-09-14) — this specific number is from a secondary source, treat as **[unverified]** pending Meta's own rate-limit page.

**Geography.** No Saudi/Egypt-specific restriction found in any source; the API is global. **[unverified]** in the sense that no source explicitly confirms KSA/Egypt, but nothing suggests a regional block, and Meta operates fully in both markets (both have large ad markets there).

**Cost.** Free — no paid tier for Graph API calls themselves.

### 1.2 Facebook Page Public Content Access

Formerly called Page Public Metadata Access; that older feature has been **superseded** by "Page Public Content Access" and Meta's docs say apps already approved for the new feature cannot even request the old one. Source: [Page Public Metadata Access — Meta for Developers](https://developers.facebook.com/docs/features-reference/page-public-metadata-access/) (retrieved 2026-09-14, page content partly in Arabic locale).
- Requires **App Review + Business Verification**, plus possibly additional contracts before data access is granted.
- Historically this feature was the basis for tools like CrowdTangle to read public Page post engagement. **CrowdTangle was shut down in August 2024**, and its replacement, the **Meta Content Library / Content Library API**, is gated to "a qualified academic or non-profit institution" via ICPSR at the University of Michigan — not available to commercial agencies. Sources: [A First Look at Meta's New Content Library API](https://socialmedialab.ca/web/2024/03/25/a-first-look-at-metas-new-content-library-and-content-library-api/), [Meta just closed a vital online research tool](https://www.uts.edu.au/news/2024/08/meta-just-closed-vital-online-research-tool) (retrieved 2026-09-14).
- **Conclusion:** even if Al-Marketer got Page Public Content Access approved (uncertain, commercial use case, no guarantee of approval), the richer CrowdTangle-style tooling for reading competitor Page post engagement is now researcher-only. Treat Facebook Pages as a weak channel for official API data; assisted browsing is the practical fallback for Facebook.

### 1.3 YouTube Data API v3

The clean, reliable, fully free option.
- **Auth**: a simple API key from Google Cloud Console (no OAuth, no app review) is sufficient for public read data. Source: [YouTube Data API Overview](https://developers.google.com/youtube/v3/getting-started) (retrieved 2026-09-14).
- **Quota**: default **10,000 units/day** per Cloud project, no monetary cost. `channels.list` and `videos.list` each cost **1 unit** per call (can batch up to 50 IDs per call); `search.list` costs 100 units (avoid it — use uploads-playlist traversal instead for enumerating a channel's videos). Source: [Channels: list — YouTube Data API](https://developers.google.com/youtube/v3/docs/channels/list), [Understanding the YouTube Data API v3 Quota System](https://docs.expertflow.com/cx/4.9/understanding-the-youtube-data-api-v3-quota-system) (retrieved 2026-09-14).
- **Data available for ANY public channel/video, no permission from the owner needed**: `channels.list` → subscriberCount, viewCount, videoCount; `videos.list` (`part=snippet,statistics`) → per-video `viewCount, likeCount, commentCount, publishedAt`, title, description. This is confirmed explicitly: *"An API key covers public channel and playlist data... you can access channel statistics for any public channel without special permissions."* Source: search synthesis of [Channels: list](https://developers.google.com/youtube/v3/docs/channels/list) and [Beyond the YouTube Data API — ChannelCrawler](https://channelcrawler.com/insights/beyond-the-youtube-data-api-access-historical-channel-data-trends-channelcrawler) (retrieved 2026-09-14).
- **Caveat**: `dislikeCount` has been hidden publicly since 2021 (not confirmed in this session but well-established prior knowledge — flag **[unverified in this session]**). Full historical Analytics (e.g., traffic sources, audience retention) requires OAuth and is scoped to channels you own — irrelevant here since you only need public post-level counts.
- **Verdict: best and simplest official path of all seven platforms.**

### 1.4 TikTok

Four distinct TikTok developer surfaces, none of which give a commercial agency free access to a competitor's organic post-level metrics:

- **Display API**: `scope=user.info.basic,video.list` — but this only returns videos for **the TikTok user who explicitly logged in and authorized your app via Login Kit**. It is built for embedding a user's own content, not for looking up arbitrary other accounts. Source: [TikTok for Developers — Display API Get Started](https://developers.tiktok.com/doc/display-api-get-started) (retrieved 2026-09-14).
- **Research API**: restricted to **qualifying academic institutions** (US/EEA/UK/Switzerland), EU-registered non-profits, and Brazilian academic/non-profit youth-safety researchers. TikTok's own FAQ states explicitly: *"creators, advertisers, and commercial users are not eligible for access to the Research Tools."* Capped at 1,000 requests/day even for approved researchers, and commercial use of the data is prohibited outright — using it for an agency's client work would violate the terms even if access were somehow obtained. Sources: [TikTok Research API FAQ](https://developers.tiktok.com/docs/en/research-api-faq), [TikTok Research Tools Terms of Service](https://www.tiktok.com/legal/page/global/terms-of-service-research-api/en) (retrieved 2026-09-14). Available metrics if it were accessible: `like_count, comment_count, view_count, share_count, create_time`.
- **Commercial Content API**: part of the ad-transparency toolset — returns ad creatives, ad metadata (targeting, spend ranges, run dates), advertiser names. Not organic post data, and rate-limited to prevent bulk collection. Source: [TikTok — Guide to Using the Commercial Content API](https://developers.tiktok.com/doc/commercial-content-api-getting-started) (retrieved 2026-09-14).
- **Creative Center**: a public web tool (not really an API for this purpose) showing trending/top-performing *ads*, not a given competitor's own organic account stats.
- **Verdict: no free official channel exists for TikTok competitor post metrics.** Assisted browsing (capturing TikTok's own web JSON, §2) is the only realistic legitimate route.

### 1.5 LinkedIn

- The only broadly available product, the **Community Management API**, grants permissions like `r_organization_social`, `r_organization_admin`, `r_organization_social_feed` — every one of them scoped to *organizations you administer* (`ADMINISTRATOR` role required). There is no permission that reads posts/engagement of a company Page you don't manage. Source: [LinkedIn — Increasing Access (Microsoft Learn, moniker li-lms-2026-08)](https://learn.microsoft.com/en-us/linkedin/marketing/increasing-access?view=li-lms-2026-06) (retrieved 2026-09-14).
- Two access tiers (Development → Standard) exist but both are still restricted to your own administered Pages/ad accounts — upgrading tiers doesn't unlock competitor data, it just removes call-volume caps (Development tier: 500 calls/app/24h, 100 calls/member/24h).
- The **Audience Insights API** and **Media Planning API** are further gated to hand-picked partners by additional LinkedIn evaluation, and the **Company Intelligence API is not accepting new applications** at all. No path there either.
- **Verdict: no official API path exists for competitor Company Page posts/metrics.** LinkedIn is also, per multiple sources, the most aggressive platform about detecting and banning automated browsing (see §2.3) — so it is the highest-risk platform in this whole project for the assisted-browsing approach, and should be done the most conservatively (slow, manual-triggered capture, low volume).

### 1.6 X (Twitter)

- As of **February 2026**, X **retired free/Basic/Pro subscription tiers for new developers** and moved to pure **pay-per-use pricing**, no free tier, no monthly minimum. Sources: [Announcing the Launch of X API Pay-Per-Use Pricing](https://devcommunity.x.com/t/announcing-the-launch-of-x-api-pay-per-use-pricing/256476), official pricing doc [X API pay-per-usage pricing and credits](https://docs.x.com/x-api/getting-started/pricing) (retrieved 2026-09-14).
- Rates: **$0.005 per post read**, **$0.010 per user profile lookup**, $0.001 for "owned reads" (your own posts/bookmarks — not applicable to competitors), post creation $0.015 (or $0.20 if it contains a link). Capped at 3,000,000 post reads/month on pay-per-use before requiring an Enterprise plan. Legacy Basic ($200/mo, 50k posts/month at app level) and Pro ($5,000/mo) tiers are being sunset/retired for existing subscribers through 2026.
- **This is technically an official API for reading another account's posts and public metrics (likes, replies, etc. via `public_metrics` on the post object) — but it is not free.** Given the project's zero-paid-software constraint context and small volume needed (a handful of competitors, periodic checks), this could still be cheap in absolute terms (e.g., checking 3 accounts × ~20 recent posts weekly ≈ 60 reads/week ≈ $0.30/week), but it is a recurring paid cost, not a free integration.
- **Verdict: usable but paid — treat as a low-priority/optional line item, not a "free" official path.** If avoided, assisted browsing on X's public timeline (logged into the agency's own account) is the free fallback.

### 1.7 Snapchat

- Snap's developer surfaces are the **Marketing API** (ads), **Snap Kit / Login Kit** (in-app identity/sharing), and the **Public Profile API**, which is explicitly a **partner/creator-opt-in program**: basic discovery metrics are described as "accessible to all Public Profiles" but enhanced insights need the creator to "opt-in to data sharing or OAuth into partner platforms." Source: [Public Profile API — Snap for Developers](https://developers.snap.com/marketing-api/Public-Profile-API/Introduction) (retrieved 2026-09-14).
- Nothing in the docs suggests an arbitrary third party (an agency with no relationship to the target business) can pull post-level metrics for a competitor's Snapchat Public Profile without that profile's consent/partnership. **[unverified]** in the strict sense that the docs don't explicitly say "no," but the described model (opt-in/OAuth-gated enhanced data) strongly implies competitor-without-consent access isn't supported.
- **Verdict: no practical official path.** Snapchat is also a mobile-app-first platform, which additionally makes browser-based assisted capture harder than Instagram/TikTok/Facebook/LinkedIn/X (all of which have usable desktop web apps). Given Egypt/Saudi B2B marketing-agency context, Snapchat is likely a low-priority platform anyway; treat as out of scope unless a specific client demands it, and fall back to manual screenshots from the mobile app if ever needed.

## 2. Assisted-capture techniques (human browsing + app records what's on screen)

### 2.1 Playwright: `launchPersistentContext` vs `connectOverCDP`

- **`launchPersistentContext(userDataDir, options)`** launches a dedicated Chromium/Chrome profile with its own `userDataDir` (cookies, localStorage, login session persist across runs). This is the natural fit for "a dedicated agency browser profile, logged into the agency's own Instagram/TikTok/etc. accounts" — one clean, isolated, reusable profile per platform account. Source: [BrowserType | Playwright](https://playwright.dev/docs/api/class-browsertype) (retrieved 2026-09-14).
- **`connectOverCDP(endpointURL)`** attaches Playwright to an **already-running** browser (e.g., the employee's real day-to-day Chrome, launched with `--remote-debugging-port`) via the Chrome DevTools Protocol. This lets the human browse normally in their real, already-logged-in browser while the app passively observes/records network traffic and DOM — the closest fit to "human browses, app records what's on screen." Source: [BrowserType | Playwright](https://playwright.dev/docs/api/class-browsertype), and a practical write-up [Attaching Playwright to a Running Browser Profile Without Losing Account Context](https://dev.to/web4browser/attaching-playwright-to-a-running-browser-profile-without-losing-account-context-bje) (retrieved 2026-09-14).
- **Caveats found:**
  - Chrome has tightened policy against automating the **default** Chrome user profile — pointing `userDataDir` at the real default "User Data" folder can cause pages not to load or Chrome to exit. Use a **separate, dedicated profile directory** either way. Source: same Playwright issue thread, [GitHub microsoft/playwright#35836](https://github.com/microsoft/playwright/issues/35836) (retrieved 2026-09-14).
  - With `connectOverCDP`, "connected" doesn't guarantee "correct account/session" — a dev write-up specifically warns *"the script may connect successfully, run correctly, and still operate inside the wrong account environment... connected should never be treated as verified"* — i.e., always assert on-screen who's logged in before recording. Source: [Debugging Playwright CDP Sessions](https://dev.to/zp_4579/debugging-playwright-cdp-sessions-that-lose-cookies-and-proxy-context-1bm6) (retrieved 2026-09-14).
  - **Recommendation for this project**: `launchPersistentContext` with a dedicated agency profile per platform is simpler, more reproducible, and keeps the automation profile fully separate from any employee's personal browser — lower risk of cross-contaminating personal sessions/cookies, and easier to reason about "this profile only ever does agency research." `connectOverCDP` is more appropriate only if the workflow genuinely requires the human to drive their own everyday browser session.

### 2.2 Capturing platform JSON responses vs parsing DOM

- Instagram, TikTok, Facebook and LinkedIn's web apps already fetch the post/profile data as **JSON via internal GraphQL/XHR endpoints** (e.g., Instagram's `/graphql/query`) as the human scrolls/views — the page renders from this JSON. Playwright's `page.on('response', ...)` (or `route`/`waitForResponse`) can capture these responses **without any DOM scraping or fragile CSS selectors**, just by listening while the human browses normally. Sources: [GitHub — instagram-graphql-scraper](https://github.com/FaustRen/instagram-graphql-scraper), [DEV — Chrome extension network interception for Instagram](https://dev.to/hamdi_laadhari/chrome-extension-network-interception-the-modern-way-to-scrape-instagram-and-beyond-49bl), [DEV — GraphQL API recon with mitmproxy](https://dev.to/fx2301/graphql-api-recon-with-mitmproxy-2f5d) (retrieved 2026-09-14).
- **Advantages of network capture over DOM parsing**: structured, complete fields (exact like/comment counts, ISO timestamps, media type) rather than fuzzy text extraction from rendered UI (which uses abbreviated numbers like "12.3K" and locale-formatted relative dates ("2h", "منذ يومين")); resilient to UI redesigns since the underlying data contracts change less often than markup/CSS; no need to wait for animations/lazy-render before reading.
- **Practical approach for this project**: `launchPersistentContext` → human logs in once (session persists) → human opens the target profile / scrolls posts at a normal pace → app's response listener filters for the relevant GraphQL/XHR endpoints and pulls out `like_count`, `comment_count`, `taken_at`/`timestamp`, `caption`, media type, view count where present → app writes to a local evidence store. Nothing is submitted back to the platform (no writes), keeping the automation surface strictly read-only/observational.
- **Detection/ban risk framing**: this approach is lower-risk than a logged-out headless scraper hitting endpoints directly and iterating URLs programmatically at machine speed, because (a) it's a real, persistent, cookie-bearing browser session — same fingerprint a human's browser would present; (b) request cadence is bounded by actual human scroll/click speed, not a loop; (c) it's not bypassing any login wall (that's the whole reason for using the agency's own logged-in account) or CAPTCHA. It is still **automated collection of data through a logged-in session**, which is the exact fact pattern platform ToS provisions on "automated means"/"scraping" typically target (see §3) — so the legal risk is about the *logged-in automation* itself, not about circumventing any technical barrier.

### 2.3 Open-source/free browser extensions for "export while you browse"

Found several Chrome extensions that fit the "human browses normally, extension exports what's visible" pattern, though none are confirmed fully open-source (license unverified for each):
- **InsightSocial** (Facebook/Instagram/TikTok/X/LinkedIn/Threads scraper, CSV/JSON export, "runs inside your normal browser session and mimics human scrolling"). Source: [GitHub — insightsocialxyz/insightsocial](https://github.com/insightsocialxyz/insightsocial) (retrieved 2026-09-14) — this one **is** on GitHub, so likely genuinely open-source; worth vetting the code before use.
- **I-Social Scraper** (Chrome Web Store) — claims all processing happens locally on-device.
- Various "TikTok Scraper: Export Users, Posts, Comments" Chrome extensions (Chrome Web Store).
Source list: search results under [TikTok Scraper — Chrome Web Store](https://chromewebstore.google.com/detail/tiktok-scraper-export-use/ophbgcffpadkemigbopiaohepaenkopm), [I-Social Scraper — Chrome Web Store](https://chromewebstore.google.com/detail/i-social-scraper-export-p/ddijhlpnokdnogjedjpemidaoicflael) (retrieved 2026-09-14).
**Caution**: third-party extensions need their own permission review (they often request broad host permissions and could themselves exfiltrate the agency's logged-in session cookies to their own servers) — **prefer the self-built Playwright network-capture approach** over installing an unvetted extension with access to logged-in agency accounts, unless the extension's source is fully readable and audited (e.g., the GitHub one above) — this keeps everything inside the "free/open-source only" constitutional rule and inside the agency's own control.

### 2.4 Practical safety tips (synthesized from LinkedIn-automation risk write-ups, generalized to all platforms)

Source cluster: [LinkedIn automation safety guide 2026](https://getsales.io/blog/linkedin-automation-safety-guide-2026/), [Is LinkedIn Automation Safe in 2026?](https://connectsafely.ai/articles/is-linkedin-automation-safe-tos-scraping-guide-2026), [How to Scrape LinkedIn in 2026 Without Getting Banned](https://linkedapi.io/guides/how-to-scrape-linkedin) (retrieved 2026-09-14):
- **Use dedicated agency accounts**, not any employee's personal/primary account, for the browsing profile — isolates ban/restriction blast radius, and matches the plan's own design.
- **Human-driven pace, not scripted loops**: sources contrast "50 profile views in 3 minutes" (flagged as clearly non-human) against "15 profile views over 2 hours" (reads as human). Keep the tool strictly assistive (records what a human is already looking at) rather than auto-navigating a list at machine speed.
- **Low volume**: a handful of competitor profiles, checked periodically (e.g., weekly/monthly for a proposal), is exactly the kind of low-volume, human-paced usage that's described as low-risk versus the "mass, high-velocity" patterns (e.g., 2,500+ profiles) that trigger platform defenses.
- **Avoid the highest-detection category**: the same research flags **browser extensions as "the most dangerous category" of automation tooling on LinkedIn specifically** — reinforces preferring the audited/self-built Playwright approach for LinkedIn in particular.
- **Vary timing, skip odd hours**: sending/viewing activity concentrated in unnatural windows (e.g., middle-of-the-night bursts) is a named red flag; since this is a human manually browsing during work hours anyway, this is naturally satisfied.
- **General fingerprinting note**: detection combines IP reputation, TLS/HTTP fingerprinting, browser fingerprinting, and behavioral analysis — a normal residential/office IP and an unmodified real browser (not headless, not obviously automated) reduces several of these signals versus a cloud-hosted headless scraper. Source: [Web Scraping Without Getting Blocked: 2026 Guide — ScrapingBee](https://www.scrapingbee.com/blog/web-scraping-without-getting-blocked/) (retrieved 2026-09-14).

## 3. Legal / ToS landscape 2024–2026 (not legal advice)

### 3.1 Meta Platforms, Inc. v. Bright Data Ltd. (N.D. Cal., ruling **January 23, 2024**)

Judge Edward M. Chen granted Bright Data summary judgment. Meta argued Bright Data breached Facebook/Instagram Terms of Service by scraping public data (while **logged out**) and reselling it, including a "survival clause" meant to bind Bright Data even after it closed its Meta accounts. The court held: (a) scraping conducted **while logged out** is not governed by the ToS at all, because a logged-out scraper is not acting as a "user" bound by those terms — the contract-based claim over logged-out collection of public data failed; (b) the survival clause purporting to bind a former account holder to platform terms in perpetuity, for logged-out activity untethered to any of the account holder's continued use, was unenforceable. Sources: [Lowenstein Sandler — Meta v. Bright Data Ruling](https://www.lowenstein.com/news-insights/publications/client-alerts/meta-v-bright-data-ruling-has-important-implications-for-webscraping-activities-by-investment-advisers-im), [Courthouse News — Federal judge rules against Meta](https://www.courthousenews.com/federal-judge-rules-against-meta-in-data-scraping-case/), [Technology & Marketing Law Blog — Bright Data Scores Major Victory](https://blog.ericgoldman.org/archives/2024/01/game-on-bright-data-scores-major-victory-in-web-scraping-dispute-with-meta-guest-blog-post.htm) (retrieved 2026-09-14).

**Relevance to this project**: this ruling is specifically about **logged-out** scraping — it does not bless logged-in automated collection, and Al-Marketer's planned design (browsing while logged into the agency's own account) is a materially different fact pattern that the ruling does not resolve. If anything, it implies platforms retain a stronger contractual argument against activity performed *while logged in as a user bound by the ToS* — which is exactly the assisted-browsing design here. This is the key legal nuance to carry forward: **being logged in likely brings you back under the platform's Terms of Service (contract) even though the underlying data is "public."**

### 3.2 X Corp. v. Bright Data Ltd. (N.D. Cal., Case No. C 23-03698 WHA)

- **May 9, 2024**: Judge William Alsup dismissed X's claims that Bright Data's scraping/reselling of public X data breached the ToS and other policies, holding X hadn't plausibly alleged a ToS-breach claim based on access to the public site, and that any claim based merely on *copying public data* was **preempted by the Copyright Act** (i.e., federal copyright law occupies that field, blocking a state-law contract claim aimed at the same conduct). Sources: [Morrison Foerster — Court Holds X's Claims Preempted](https://www.mofo.com/resources/insights/240604-california-federal-court-holds-x-s-claims), [IP & Media Law FKKS — Blockbuster Ruling](https://ipandmedialaw.fkks.com/post/102j7d0/blockbuster-ruling-federal-court-holds-that-copyright-act-preempts-xs-web-scrap) (retrieved 2026-09-14).
- **November 2024**: the court allowed X to amend and add claims, finding X now "plausibly alleges" that Bright Data's more sophisticated access methods caused cognizable harm — the case continued rather than ending outright. Source: [digitalpolicyalert.org — X Corp v Bright Data ruling](https://digitalpolicyalert.org/event/19822-issued-ruling-in-lawsuit-alleging-copyright-violations-concerning-data-scrapping-x-corp-v-bright-data-ltd) (retrieved 2026-09-14).
- **March 2025**: litigation still ongoing, with Bright Data countersuing on antitrust grounds over X's contract terms. Source: same digitalpolicyalert.org entry (retrieved 2026-09-14).
- **Takeaway**: reinforces that pure copying of publicly-visible facts/data faces a real (though contested and evolving) legal headwind for platforms trying to stop it via contract law, but the litigation is not fully settled and keeps evolving year to year — treat as directional, not dispositive.

### 3.3 hiQ Labs, Inc. v. LinkedIn Corp. — final outcome

- Ninth Circuit (April 2022) had already ruled, on the CFAA question, that merely violating a website's terms of use is **not enough** to trigger "without authorization" liability under the Computer Fraud and Abuse Act for scraping **publicly accessible** pages — this remains the most pro-scraping circuit precedent in the US. Source: [Justia — hiQ Labs v. LinkedIn, 9th Cir. 2022](https://law.justia.com/cases/federal/appellate-courts/ca9/17-16783/17-16783-2022-04-18.html) (retrieved 2026-09-14).
- **However**, the parties then privately **settled in December 2022**: hiQ agreed to a **permanent injunction** to stop scraping LinkedIn entirely, delete all scraped data/source code/algorithms, pay LinkedIn **$500,000**, and **stipulated** that LinkedIn could establish liability under the CFAA and California's equivalent state law, plus California common-law trespass to chattels and misappropriation — though these stipulations bind only the parties and set no precedent. Sources: [Privacy World — LinkedIn's Data Scraping Battle Ends](https://www.privacyworld.blog/2022/12/linkedins-data-scraping-battle-with-hiq-labs-ends-with-proposed-judgment/), [Proskauer — hiQ and LinkedIn Reach Settlement](https://newmedialaw.proskauer.com/2022/12/08/hiq-and-linkedin-reach-proposed-settlement-in-landmark-scraping-case/) (retrieved 2026-09-14).
- **Takeaway**: the favorable CFAA precedent (logged-out scraping of public pages ≠ automatic federal crime) survives and is good law in the 9th Circuit, but the company that won that precedent still ultimately lost the war on contract/tort grounds and was permanently barred from scraping LinkedIn. This underscores that avoiding CFAA exposure does **not** mean avoiding ToS/contract or state-tort exposure — and LinkedIn in particular has shown it will litigate scraping aggressively.

### 3.4 What this means for a small agency doing low-volume, logged-in assisted browsing

Not legal advice; general risk framing based on the above:
- **Lower risk pattern**: browsing publicly visible profile/post pages **while logged into the agency's own account**, at human pace, low volume (a handful of competitor accounts, periodic), purely to *read and record* metrics already displayed on-screen (no bypassing of login walls, no CAPTCHA circumvention, no bulk/automated crawling of thousands of profiles, no redistribution/resale of the data — internal use only for one client's proposal). This mirrors normal manual research an employee could do by hand; capturing the network JSON is just a more reliable way of writing down what a human already saw.
- **Higher risk pattern**: high-volume automated iteration (many accounts, high frequency, unattended overnight runs), reselling/publishing the collected data externally, circumventing technical access controls (logins, CAPTCHAs, rate-limit evasion via proxies/IP rotation), or continuing to use accounts after a platform has terminated/warned them — all of these move closer to the fact patterns platforms have successfully litigated (hiQ's final outcome, ongoing X v. Bright Data claims about "sophisticated efforts to access").
- Being **logged in** matters legally: Meta v. Bright Data's holding turned specifically on the scraper being logged *out*; a logged-in agency account is a "user" who has agreed to the platform's Terms of Service, so **the ToS's restrictions on automated collection likely do apply contractually** even though this ruling doesn't itself create liability — worst case for breach of a platform's ToS is typically account/API termination and (rarely, for large-scale commercial resale operations) civil suit, not criminal liability. For a small agency's internal, low-volume, non-resold research use, the realistic downside is the agency's dedicated research accounts getting rate-limited or suspended — not litigation exposure comparable to Bright Data or hiQ's commercial-scale operations.
- All three cases (Bright Data ×2, hiQ) involved **commercial data resale/brokerage operations at scale** — a fundamentally different risk profile than an agency reading a few competitor profiles for one client's own proposal and not republishing the raw data.

### 3.5 Saudi PDPL and Egypt PDPL — brief relevance

- **Saudi Arabia's PDPL** applies to processing of **personal data of individuals** (natural persons) residing in Saudi Arabia, by any controller (including foreign entities) processing such data — with an explicit carve-out for purely personal/family use. Sources: [Securiti — Understanding Saudi Arabia's PDPL](https://securiti.ai/saudi-arabia-personal-data-protection-law/), [DLA Piper — Data protection laws in Saudi Arabia](https://www.dlapiperdataprotection.com/?c=SA) (retrieved 2026-09-14).
- **Egypt's Law No. 151 of 2020** similarly protects personal data of natural persons processed electronically, with extraterritorial reach to foreign entities processing data of individuals located in Egypt, and a compliance/enforcement runway extending into **October 2026** under newer Executive Regulations. Sources: [Kennedys Law — Egypt's PDPL compliance countdown](https://www.kennedyslaw.com/en/thought-leadership/article/2026/egypt-s-personal-data-protection-law-the-compliance-countdown-has-begun/), [Law No. 151 of 2020 (English translation, ACC)](https://www.acc.com/sites/default/files/program-materials/upload/Data%20Protection%20Law%20-%20Egypt%20-%20EN%20-%20MBH.PDF) (retrieved 2026-09-14).
- **Relevance to this project**: the core metrics being collected (a business's follower count, post-level like/comment/view counts, post dates) are **business-level/aggregate metrics about a company account, not personal data about an identifiable individual**, so the PDPLs' core machinery (consent, data-subject rights) is not squarely engaged by that layer of data. However, **captions/comments can incidentally contain personal data of identifiable individuals** (a named customer's comment, a tagged employee's photo) — if such content is stored, both PDPLs' general obligations (lawful basis, data minimization, security, not keeping data longer than needed) would apply to that incidental personal data. **Practical mitigation**: store only the aggregate/engagement numbers, dates, and captions needed for the proposal; avoid deliberately harvesting commenters' identities; treat any retained data as subject to normal data-minimization/security practice; this is a brief orientation only — not a compliance opinion, and neither PDPL's scraping-specific case law was found in this research (none surfaced in search).
