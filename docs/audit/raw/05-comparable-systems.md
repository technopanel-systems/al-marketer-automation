# Comparable systems audit: research agents, Arabic/RTL generation, rule engines

Retrieval date for all sources below: 2026-09-14, via web search and GitHub file fetches, unless a specific in-text date is cited from a paper/changelog.

Scope note: this is a comparison of *architecture and mechanisms*, not a recommendation to rewrite al-marketer-automation. Where a source file could not be fully retrieved (private/blocked/paywalled), it is marked `[unverified]` and the claim is qualified.

## 1. Evidence-backed / hallucination-resistant research agents

### 1.1 GPT Researcher (github.com/assafelovic/gpt-researcher)

- Repo: https://github.com/assafelovic/gpt-researcher (retrieved 2026-09-14)
- Source inspected: `gpt_researcher/skills/researcher.py` (raw file, retrieved 2026-09-14): https://raw.githubusercontent.com/assafelovic/gpt-researcher/master/gpt_researcher/skills/researcher.py

**Citation verification**: GPT Researcher does **not** verify citations character-for-character against source text. The pipeline is: scrapers pull full page text via `scraper_manager.browse_urls()` into `{"url": url, "raw_content": raw_content}` records → this raw content is concatenated straight into the LLM context (`_combine_mcp_and_web_context()` formats a citation as `"*Source: {title} ({url})*"`) → the LLM is trusted to (a) decide what to say and (b) attach the right URL to it. There is no post-hoc step that re-opens the source and checks the quoted/paraphrased text actually appears there. This is the "trust the model's citation" pattern, the opposite of what al-marketer-automation's evidence pipeline does (save evidence page text, then have code independently re-check every AI-produced quote against the saved text after Arabic normalization).

**Parallelization / merging**: Sub-queries run concurrently via `asyncio.gather(*[self._process_sub_query(...) for sub_query in sub_queries])`; each retriever class also runs independently. Merging is naive concatenation — `' '.join(context)`, `'\n\n'.join(...)` — with **no deduplication, no conflict resolution, and no coherence check** between what different parallel branches found. The final report's coherence is entirely the LLM's responsibility at write time.

**Human-in-the-loop**: No evidence of a gating step in this file; GPT Researcher's documented product design is "give it a topic, get a report," i.e., a single-shot pipeline, not a staged human-approval workflow. [unverified beyond this file — the wider repo may have a "human_edit"/deep-research config flag, but nothing comparable to a 3-gate approval chain was found in search results.]

**If we adopted approach X from GPT Researcher**: nothing here is worth borrowing — it's a weaker citation model than what al-marketer-automation already has. The one thing worth noting for contrast in an audit doc: GPT Researcher's `asyncio.gather` fan-out/fan-in for sub-queries is a simpler, less structured version of what the in-house system already does with its 3 parallel Sonnet research calls; the in-house system's requirement that every fact cite a real saved evidence-page id + verified quote is strictly stronger than anything in GPT Researcher's design.

### 1.2 Stanford STORM / Co-STORM (github.com/stanford-oval/storm)

- Repo: https://github.com/stanford-oval/storm (retrieved 2026-09-14)
- Files inspected: `knowledge_storm/interface.py` (https://github.com/stanford-oval/storm/blob/main/knowledge_storm/interface.py) and `knowledge_storm/collaborative_storm/modules/co_storm_agents.py` (https://github.com/stanford-oval/storm/blob/main/knowledge_storm/collaborative_storm/modules/co_storm_agents.py), both retrieved 2026-09-14
- Paper: Shao et al., "Assisting in Writing Wikipedia-like Articles From Scratch with Large Language Models," arXiv:2402.14207 (NAACL 2024), HTML retrieved 2026-09-14: https://arxiv.org/html/2402.14207v2

**Citation verification**: STORM measures citation quality with two automated metrics — **citation recall 84.83%** and **citation precision 85.18%** — computed by having **Mistral‑7B‑Instruct judge whether the cited passage entails the generated sentence** (an LLM-as-judge NLI-style check), not a character-for-character string match against source text. This is meaningfully different from al-marketer-automation's approach: STORM checks *semantic entailment* (is the citation topically/logically supportive), which still leaves ~15% of sentences citing something that doesn't actually support the claim (the paper attributes these failures to "improper inferential linking," "inaccurate paraphrasing," and "citing irrelevant sources" — i.e., plausible-looking but ungrounded citations slip through). Al-marketer-automation's normalized exact-quote-match verification is stricter and catches a different, arguably more important class of failure (fabricated quotes), though it wouldn't catch STORM's "irrelevant but literally-present quote" failure mode — the two approaches are complementary, not equivalent.

**Multi-agent parallelization/merging**: STORM/Co-STORM's mechanism is a simulated multi-perspective conversation: distinct "expert" agents (roles derived automatically from related-topic analysis) each converse with a "Wikipedia writer" agent grounded in retrieved sources, and a `Moderator` class injects fresh unused snippets (reranked by dissimilarity to already-cited info) to avoid redundant coverage. Merging into the shared `KnowledgeBase`/"mind map" (Co-STORM) is by **accretion and redundancy-avoidance**, not conflict resolution — the code has no logic to detect or reconcile two experts making contradictory claims; it's designed for complementary (different-facet) contributions, not adversarial fact-checking.

**Human-in-the-loop**: The base STORM interface (`interface.py`) has **no gating mechanism** — outline generation → article polishing is fully automated. Co-STORM adds an interactive mode where a human can steer the *conversation* (ask questions, redirect focus) mid-run, which is closer to "collaborative co-drafting" than to a discrete approve/reject gate on a finished artifact. There is nothing structurally equivalent to al-marketer-automation's 3 discrete, artifact-level, non-bypassable human approval gates.

**If we adopted approach X from STORM**: an entailment-style secondary check (a fast/cheap model asked "does this cited passage actually support this specific claim," independent of the exact-quote match) would catch a failure class the current exact-quote verifier structurally cannot catch — a quote can be 100% verbatim-accurate and verified, yet still be irrelevant or misleading in context. Since al-marketer-automation already runs a second-opinion reviewer step for diagnosis (fresh-context Sonnet review of each claim+evidence), the same "independent judge, evidence only, no reasoning trace" pattern used there could be extended one step earlier, to the research/fact-extraction stage, as a supplement (not replacement) to the existing exact-quote verifier.

### 1.3 LangChain open_deep_research (github.com/langchain-ai/open_deep_research)

- Repo: https://github.com/langchain-ai/open_deep_research (retrieved 2026-09-14). Note: the README states the repo was **archived on 2026-08-21**, and describes a "legacy" plan-and-execute/multi-agent implementation as superseded by a "current" implementation.
- Files inspected: `README.md` (https://github.com/langchain-ai/open_deep_research/blob/main/README.md) and `src/open_deep_research/deep_researcher.py` (https://github.com/langchain-ai/open_deep_research/blob/main/src/open_deep_research/deep_researcher.py), both retrieved 2026-09-14

**Citation verification**: No citation extraction or verification logic exists in `deep_researcher.py`. Findings are compressed per-researcher (`compress_research`) and concatenated into `raw_notes_concat = "\n".join(...)` for the supervisor; sourcing/citations are left to the final report-writing LLM call to produce from context, with **no independent check against retrieved text**.

**Parallelization/merging**: The **current** architecture is a supervisor–researcher pattern: the supervisor calls a `ConductResearch` tool, which fans out `researcher_subgraph.ainvoke(...)` calls via `asyncio.gather`, bounded by `configurable.max_concurrent_research_units`. Each sub-researcher independently compresses its own findings before returning; the supervisor aggregates the *compressed* summaries (not raw text) plus a separate concatenation of raw notes for the final writer. This is a more structured fan-out/fan-in than GPT Researcher's (per-researcher compression step before merge, plus an explicit concurrency cap) but still has no fact-level conflict detection.

**Human-in-the-loop**: The **legacy** plan-and-execute workflow supports a single approval point — a human reviews/edits the *report plan* (the section outline) before the (slow) research phase runs, and can send free-text feedback to regenerate the plan before approving it (`README.md`; a related fork, https://github.com/piotrgoral/open_deep_research-human-in-the-loop, retrieved 2026-09-14, focuses specifically on this). The **current** supervisor-based architecture inspected in `deep_researcher.py` has **no human approval step at all** — it runs supervisor → parallel researchers → final report with only an optional initial clarification question to the user before research starts. So the project's own trajectory moved *away* from human gating, not toward more of it, as it was optimized for autonomous throughput.

**If we adopted approach X from open_deep_research**: the concurrency-capped supervisor/sub-researcher fan-out with a **separate compression step per researcher before merge** (rather than raw-content concatenation) is worth noting as a pattern for the in-house system's 3 parallel Sonnet research calls, if/when that step is revisited: compressing each parallel branch's findings independently before the merge step (rather than concatenating raw evidence text) could reduce prompt bloat and cross-contamination between branches, while leaving the mandatory per-fact citation+quote-verification untouched. This is a token-budget/quality-of-merge optimization, not a change to any constitutional rule.

**Summary for area 1**: none of the three projects verify citations against source text the way al-marketer-automation does (normalized exact-quote match, code-checked). GPT Researcher and current open_deep_research trust the model's citation entirely; STORM is the most rigorous of the three, but checks semantic entailment via a second LLM, not literal quote presence. None of the three has anything structurally equivalent to 3 discrete human approval gates with staleness tracking — open_deep_research's legacy single-plan-approval step is the closest analog, and the project moved away from it in its current design.

## 2. RTL / Arabic document/slide generation pipelines

**Finding: no actively maintained open-source project does Arabic/RTL slide or document generation to production quality as a dedicated, general-purpose tool.** What exists instead falls into three buckets, none of which is "point it at content and get a correct Arabic deck/doc":

1. **General-purpose PDF/document libraries bolting on Arabic support, explicitly marked experimental.** ReportLab (the most established Python PDF library, in active use since the early 2000s) shipped its **first** shaping+RTL support only in **v4.4.0, April 2025** (https://docs.reportlab.com/releases/notes/whats-new-44/, retrieved 2026-09-14; corroborating changelog summary via search, retrieved 2026-09-14), using HarfBuzz for glyph shaping. The project's own docs describe this as "preliminary support for right-to-left scripts (e.g. Arabic + Hebrew)" and state it should be "considered experimental" — i.e., as of the most mature general PDF library in this space, Arabic/RTL is ~18 months old and self-described as not production-solid.
2. **Point patches for specific frameworks' broken RTL, not full pipelines.** E.g., a community-built `@react-pdf-rtl` patch exists specifically because `@react-pdf/renderer`'s RTL/Hebrew-Arabic rendering has been broken since 2019 (blog post retrieved 2026-09-14: https://techresolve.blog/2026/03/09/i-built-a-library-to-fix-rtl-hebrew-arabic-text/) — this is a bug-fix library, not a document-generation system, and it's targeting a years-old known defect in a mainstream tool, illustrating how under-served this is even in popular libraries.
3. **General reshaping utilities, not layout/generation systems.** `arabic_reshaper` + `python-bidi` (Python) handle glyph joining and bidi reordering for a string, but say nothing about page layout, slide layout, mixed-script line-breaking, or PDF/PPTX generation — they're inputs a generation pipeline must still be built around (Medium walkthrough retrieved 2026-09-14: https://medium.com/@yahdi/properly-rendering-arabic-text-in-python-and-pdf-with-arabic-reshaper-and-bidi-dosensibuk-com-3ce79499dff8).

A search specifically for "Arabic RTL slide deck generator" (2026-09-14) surfaced no dedicated production-grade hit; the closest were: `univer-rtl` (github.com/riyadhali/univer-rtl) — a **fork** of the Univer office suite adding Arabic/RTL to spreadsheets/docs/presentations, whose own description frames it as still evolving ("full worksheet-level RTL mirroring for slides" not yet complete) — and generic AI slide generators (SlideDeck AI, Presenton) that are Latin/LTR-first with no dedicated Arabic engineering found in their docs. Browser rendering engines (Chromium/WebKit) — which is what al-marketer-automation already uses (headless Chromium HTML→PDF) — and browser-based PDF engines like dompdf.js (which explicitly leans on "a real typesetting engine" for `dir`-aware bidi and Arabic ligatures, per https://dompdfjs.lisky.com.cn/articles/rtl-text-guide-en.html, retrieved 2026-09-14) are, per this research, the most mature RTL/bidi+shaping engines generally available today — more mature than any of the document-generation libraries built on top of them. That is itself the finding: **the correct current strategy is "render via a browser engine and control layout with CSS logical properties/font-loading waits," which is what this system already does — there is no more mature off-the-shelf alternative to adopt.**

**If we adopted approach X from project Y**: there isn't a project Y here to adopt from for the core rendering problem — the in-house system's own choice (HTML/CSS via headless Chromium, with explicit font-load-before-print and overflow-driven relayout) already tracks the field's actual state of the art better than any of the dedicated "Arabic document generator" libraries found. The one concrete, narrow thing worth borrowing is defensive: `@react-pdf-rtl`'s existence as a 2026 bug-fix for a 2019-era defect is a reminder to keep a regression test suite specifically for mixed Latin/Arabic runs (numbers, brand names inside Arabic sentences) — exactly the kind of case that breaks first and gets "fixed" years later elsewhere — which the codebase's constitutional rule about isolating Latin names/numbers already anticipates; treat that as validated by outside evidence, not as a gap.

## 3. Rule/decision-engine libraries (Node.js) for confirmed-facts → deterministic scope/schedule selection

### 3.1 json-rules-engine (github.com/CacheControl/json-rules-engine)

- Docs inspected: `docs/rules.md` (https://github.com/CacheControl/json-rules-engine/blob/master/docs/rules.md, retrieved 2026-09-14)

Supports: fact/operator/value conditions, `all`/`any`/`not` boolean composition (nestable), named condition references, dynamic parameters/JSON-path fact traversal, fact-to-fact comparisons, integer `priority` (higher runs first; equal-priority rules run in parallel), and `success`/`failure` events. It does **not** document dependency-graph scheduling between rules (no declared "rule B requires output of rule A" edges beyond ad hoc fact computation order) and has **no concept of an approval gate or staleness/versioning** of anything — it's a pure condition→event evaluator with no persistence or workflow-state model at all.

### 3.2 GoRules / Zen Engine (github.com/gorules/zen)

- Sources: main README (https://github.com/gorules/zen/blob/master/README.md) and Node.js reference docs (https://docs.gorules.io/reference/nodejs), both retrieved 2026-09-14

Zen Engine's JDM (JSON Decision Model) format **does** support composing a decision as a graph of node types — decision tables, switch nodes, expression nodes, function nodes, and **reusable sub-decisions** (a decision node can reference another decision), so it genuinely supports dependency-style composition of decisions into a DAG, more than json-rules-engine does. However: (a) this composition is about *decision logic* wiring, not about scheduling real-world dated/dependent tasks (there's no week/date/duration concept — it evaluates in microseconds and returns a value, it isn't a project-scheduling engine); and (b) the human-approval/versioning/rollback features mentioned in GoRules marketing ("a release moves from testing to staging to production... approvals, instant rollback, and a paper trail for every change") are **platform-layer features of the commercial GoRules product**, not the open-source `zen-engine` library itself — the OSS engine is execution-only with no approval-gate or staleness concept built in.

### 3.3 Approval-gate staleness tracking: no purpose-built library found; the closest real-world analog is build-system content hashing, not workflow-engine "gates"

A targeted search for a workflow/rules library that treats "an approval becomes invalid if its upstream input changes" as a first-class, built-in concept came up empty for anything matching al-marketer-automation's specific need — this appears to be a genuine gap in the ecosystem, not a search-quality problem: workflow/BPM tools (implied by GoRules' own platform-tier framing of "approvals... paper trail") generally model human approval as a task/step, and rules engines model rules as stateless evaluators; neither tradition models **"this specific prior approval's validity is a function of a content hash of its inputs."**

The closest existing prior art for that exact mechanism is not in the human-approval-workflow space at all, but in **build-system incremental caching**:
- **dbt's `state:modified` / state comparison** computes a content hash per model (compiled SQL + config, or for sources, freshness config) and treats any node whose hash changed as "modified," with `state:modified+` selecting it and everything downstream for re-run (https://docs.getdbt.com/docs/deploy/dbt-state-about and https://docs.getdbt.com/blog/how-dbt-state-works, retrieved 2026-09-14). This is structurally the same idea as al-marketer-automation's input-fingerprint chain: a hash over upstream state that, when it changes, invalidates everything that depended on the old hash.
- **Bazel's action cache** keys a cached result by a hash of an action's declared inputs (source files, command line, env vars); a documented, known consequence is that changing even a single input (per Bazel's own issue tracker and docs, e.g. https://bazel.build/remote/caching and https://github.com/bazelbuild/bazel/issues/23841, retrieved 2026-09-14) invalidates the cache for that action and (transitively) its dependents.

Neither dbt nor Bazel frames this as a *human approval* concept — they invalidate a cached *computation result*, not a person's sign-off — but the underlying mechanism (content-hash the inputs; if the hash a downstream artifact was built/approved against no longer matches current upstream state, treat it as stale and force re-derivation) is exactly the primitive al-marketer-automation's `pipeline/gates.js` input-fingerprint/output-hash chain implements, just applied to a human-approval boundary instead of a build artifact.

**If we adopted approach X from project Y**: nothing here should replace the custom `pipeline/gates.js` — no off-the-shelf Node rules/decision engine (json-rules-engine, GoRules OSS) has an approval-gate-with-staleness concept, so building it in-house was the correct call, not a gap to fix. The one concrete idea worth borrowing from dbt specifically is **`state:modified+`'s "select the changed node and everything downstream"** as a mental model/naming convention for gate invalidation reporting: when Gate 1's input fingerprint changes, the system should be able to answer "which of Gate 2 and Gate 3's approvals are now downstream of stale data" the same way dbt answers "which models are downstream of this changed source" — if `pipeline/gates.js` doesn't already expose a single "show me everything invalidated transitively from this changed input" view (as opposed to per-gate fingerprint checks), that's a small, concrete UX/debuggability improvement worth adding, modeled on dbt's downstream-selection semantics rather than on any library dependency.

## Overall summary (one paragraph per area)

1. **Research agents**: al-marketer-automation's exact-quote, code-verified citation check (after Arabic-specific normalization) is stricter than all three comparison projects. GPT Researcher and open_deep_research's current architecture trust the model's citations outright; STORM is the strongest of the three with an automated entailment-style judge (84.83% recall / 85.18% precision) but that catches a different failure mode (irrelevant-but-present citations) than exact-quote fabrication. Worth considering: an entailment-style secondary check as a supplement to (not replacement for) the existing exact-quote verifier, reusing the system's own "fresh-context independent reviewer" pattern one stage earlier.
2. **Arabic/RTL generation**: no production-quality dedicated OSS pipeline exists; even ReportLab's Arabic/RTL support is 18 months old and self-described as experimental, and mainstream tools like `@react-pdf/renderer` have had known-broken RTL since 2019. The in-house choice of headless-Chromium HTML/CSS rendering is already using the most mature bidi/shaping engines actually available (browser engines), so there is no better off-the-shelf alternative to adopt — this absence is itself the finding.
3. **Rule/decision engines**: neither json-rules-engine nor GoRules' open-source Zen Engine has dependency-graph task scheduling (GoRules composes decision logic into a DAG, but that's not date/duration scheduling) or a human-approval-gate/staleness concept; GoRules' approval/rollback/versioning story is a paid platform feature, not in the OSS engine. The closest real analog to al-marketer-automation's fingerprint/staleness chain is build-system incremental caching (dbt `state:modified`, Bazel's action cache), which validates the custom `pipeline/gates.js` design as filling a genuine ecosystem gap rather than reinventing something available off the shelf; the one borrowable idea is dbt's "changed node + everything downstream" selection semantics as a model for a gate-invalidation-impact view.
