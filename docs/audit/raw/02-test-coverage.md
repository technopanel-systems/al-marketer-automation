# Test coverage audit — Blueprint rules S1–S14, C1–C11

Scope: `test/engine/plan.test.js`, `test/engine/content-checks.test.js`, `test/pipeline/pipeline.test.js`,
`test/render/deck.test.js`, cross-checked against `engine/checks/scope-checks.js` and
`engine/checks/content-checks.js` (implementation ids), plus supporting reads of
`engine/plan/build.js`, `engine/scope/resolve.js`, `pipeline/gates.js`, `pipeline/steps.js`,
`pipeline/run.js`, `render/render.js`, and `test/engine/text.test.js`.

## Id reconciliation

- Scope checks implemented in `engine/checks/scope-checks.js`: **S1, S2, S3, S4, S5, S6, S7, S9, S10, S11, S12, S13**.
  **S8** (verified quote/check/human confirmation) and **S14** (hash-based no-stale-approvals) are *not*
  implemented as `runScopeChecks` entries — they live in `pipeline/gates.js` (`gate1Problems`/`approveGate1`)
  and `pipeline/steps.js` (`gateState`, `inputFingerprint`/`computeState`) respectively. This is a legitimate
  separation (S8/S14 are pipeline/gate concerns, not plan-shape concerns) but means `plan.test.js`'s
  `failed(r)` helper (which only reads `r.checks`, i.e. the scope-checks array) can never surface an S8 or
  S14 regression — only `pipeline.test.js` can.
- Content checks implemented in `engine/checks/content-checks.js`: **C2, C3a/C3b/C3c (≈ Blueprint C3), C4, C5,
  C6, C7, C8, C9, C10(warning)**, plus `L1/L2/L3` (title/length rules that aren't in the Blueprint's C1–C11 list
  at all — extra, not mapped here). **C1** (fixed 01–11 section order) and **C11** (no overflow / fonts loaded /
  PDF page count = slide count) are not in `content-checks.js`; C1 is asserted in `render/deck.js`'s
  `assembleDeck`/`buildDeck` output shape and tested in `deck.test.js`; C11 is computed in `render/render.js`
  and partially asserted in `pipeline.test.js`.

## Weak-or-no coverage, ranked by production risk if silently broken

1. **C11 — no slide overflow / render.ok** (none for the overflow half): a broken overflow detector or a broken `SHRINK` retry loop would ship a client-facing PDF with cut-off or overlapping Arabic text and no test would fail. This is the most visible, most embarrassing possible failure (goes straight to a client) and currently has zero adversarial coverage.
2. **C10 — jargon explained on first use** (none): the rule as implemented doesn't even check "explained," only "present," and no test exercises even that. A proposal full of unexplained `ROAS`/`CPA`/`فانل` jargon would sail through every automated check.
3. **S8 — verified quote path** (weak at the leaf): the actual quote-vs-source verification (`verifyCitation`/`verifyQuote`) is bypassed in the only test that exercises the Gate 1 evidence gate; a regression that let *any* string count as a "verified" quote wouldn't be caught by `pipeline.test.js`, only by the narrower, disconnected `text.test.js` unit tests.
4. **A Gate 1 confirmation note becoming evidence** (untested code path): if `approveGate1`'s note→`addTextSource` logic broke, a confirmed-via-note problem would silently have no citable evidence downstream (violating S8/C7 later), and nothing would catch it at the point of breakage.
5. **S12 — max week 12 / explicit after-month-3 list** (weak): "never silently cut" is the rule's whole point, and nothing inspects `schedule.afterMonth3` directly; a regression that just dropped overflow deliverables would only be caught incidentally, and only if the specific sweep test happens to produce an overflowing schedule.
6. **C9 — leaked internal ids/jargon** (weak, partial pattern coverage): a narrowed regex (e.g. dropping the `confidence`/`capability` keyword check) would let internal scoring language leak to a client with no test failing.
7. **S3 / S4 (orphan half) — catalog/orphan integrity** (weak, incidental only): protected only by the broad all-problem-types sweep, not by a deliberate adversarial case.
8. **C3b/C3c (solutions/expected coverage)** (weak): shares code with the well-tested C2/C3a, so risk is lower, but a branch-specific bug would not be caught.
